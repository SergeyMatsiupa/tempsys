17.2    Website- und Store-View-spezifische Werte und Einstellungen hinterlegen

Das Grundgerüst haben Sie in Ihrem Magento-Shop bereits aufgebaut, und Sie verfügen nach jetzigem Stand über mehrere Store Views und einen zusätzlichen Store bzw. eine Website. Nun geht es darum, diesen Konfigurationsebenen Werte zuzuweisen. Denn ein französischer Store View gibt beispielsweise nur dann alle Einträge im Frontend auf Französisch aus, wenn Sie in der Konfiguration die Sprache anpassen. Da es in Magento viele verschiedene Bereiche gibt, in denen Sie Anpassungen vornehmen können, möchte ich Ihnen diese bzw. die dahinterliegende Funktionsweise im Schnelldurchlauf vorstellen. Als Referenz verwende ich den spanischen Store View, Sie können natürlich auch gern den französischen nehmen bzw. den Store View, den Sie bei sich angelegt haben. Wie Sie sehen werden, können Sie die Vorgehensweise dann schlussendlich auch bei Änderungen der Website adaptieren. Denn sowohl die Website als auch der Store View sind nur Konfigurationsbereiche, die sich einfach aufgrund der Hierarchie unterscheiden.

17.2.1    Produkte

Speziell wenn Sie mit verschiedenen Sprachen im Frontend arbeiten, müssen Sie natürlich auch die Produkte bzw. deren Inhalte übersetzen. Rufen Sie hierzu exemplarisch irgendein Produkt auf, das Sie angelegt haben. Ich greife auch an dieser Stelle auf meinen Lieblingsartikel »Bratpfanne Martina« zurück. Wenn Sie das Produkt aufgerufen haben, werfen Sie bitte einen Blick in die linke obere Ecke bzw. auf Abbildung 17.7.

Abbildung 17.7    Über das Dropdown-Menü »Alle Store Views« können Sie den gewünschten Stor eView auswählen.

Wenn Sie auf das Dropdown-Menü Alle Store Views klicken, öffnet sich ein neues Menü, in dem Sie nun den Store View, sprich den Konfigurationsbereich auswählen können. Vermutlich wird Ihnen zuerst die Frage durch den Kopf schießen, wo denn die andere Website bzw. der thailändische Store View geblieben ist. Bei Produkten müssen Sie, um auf den Store View zuzugreifen, das Produkt explizit der Website hinzufügen. Genau das können Sie auch innerhalb der Produktdetailansicht tun, indem Sie zum Bereich »Product in Websites« scrollen und dort die zweite bzw. weitere Website hinzufügen. Erst wenn Sie das getan haben, taucht die Website mit allen hinterlegten bzw. zugewiesenen Store Views oben in dem Dropdown-Menü auf.

Wählen Sie, ich hatte mein Referenzbeispiel »Spanisch« bereits erwähnt, bitte den Eintrag »Spanisch« aus. Daraufhin lädt Magento die Ansicht neu, und Sie befinden sich nun in dem Konfigurationsbereich »Spanisch«. Ohne auf alle Details einzugehen, haben Sie jetzt die Möglichkeit, die dargestellten Felder bzw. die dort enthaltenen Informationen abzuändern. Wenn in Spanien die »Bratpfanne Martina« z. B. »Sartén Martina« heißt, so können Sie diesen Wert einfach beim Namen hinterlegen und das Produkt speichern. Sie haben mit dieser Aktion dann nur in dem Konfigurationsbereich des Store Views »Spanisch« diesen Wert angepasst. Das heißt, in den anderen Store Views heißt das Produkt immer noch »Bratpfanne Martina«. Und das ist an sich auch die grundlegende Logik, die Magento an dieser Stelle verfolgt. Bei der Anlage eines Produktes hinterlegen Sie sozusagen die allgemeingültigen Werte, die an jeden Store View vererbt werden. Wenn Sie mehrere Store Views haben, können Sie den gewünschten Store View an dieser Stelle auswählen und die geerbten Werte editieren und anpassen. Sie müssen jedoch nicht jeden Wert anpassen, da alle Werte grundsätzlich vererbt werden. Ändern Sie jetzt ruhig ein paar Werte und Optionen ab, und machen Sie sich mit dem Mechanismus vertraut. Ich werde noch die Beschreibungstexte sowie den Preis anpassen, einfach damit Sie später im Frontend eine gewisse Unterscheidung sehen.

Speziell bei Produkten müssen Sie noch berücksichtigen, dass nicht alle Werte abgeändert werden können. Ein Lagerbestand wird beispielsweise global definiert, daher können Sie diesen auf Store-View-Ebene nicht anpassen. Auch spielen bei den Produkten die Websites keine Rolle, d. h., Sie können an dieser Stelle ausschließlich auf Store-View-Ebene Inhalte ändern und editieren, ganz im Gegensatz zur Systemkonfiguration, die sich auch auf Website-Ebene durchführen lässt.

17.2.2    Kategorien

Bei den Kategorien funktioniert die Store-View-spezifische Hinterlegung von Informationen genau wie bei den Produkten. Wenn Sie die Kategorie-Verwaltung aufrufen, werden Sie im oberen linken Bereich wiederum ein Dropdown-Menü sehen. Wenn Sie auf dieses Menü klicken, werden Sie beide Websites und alle zugehörigen Store Views sehen und können diese auswählen. Auch hier erfolgt die Anpassung wiederum auf Store-View-Ebene, d. h., Sie können die Website-Ebene erst gar nicht auswählen. Das hängt an dieser Stelle auch wieder damit zusammen, dass Magento davon ausgeht, dass Sie an dieser Stelle ausschließlich Übersetzungen vornehmen, und diese werden auf der unterste Ebene, sprich beim Store View, gepflegt.

Einzig die Ausnahme mit den Stores müssen Sie an dieser Stelle berücksichtigen. Sprich, Sie könnten theoretisch auch pro Store View einen Store anlegen, pro Store eine Root-Kategorie und somit auf der höchsten Ebene direkt die Übersetzungen hinterlegen. Das ergibt nur dann Sinn, wenn Sie pro Sprache eine komplett unterschiedliche Kategorie-Struktur haben. Denn in diesem Fall müssen Sie auf jeden Fall mit verschiedenen Root-Kategorien arbeiten und könnten diese dann, auch wenn es etwas unsauber erscheint, für die Übersetzungen nutzen.

17.2.3    Kunden

Der Vollständigkeit halber erwähne ich an dieser Stelle auch die Kunden, denn würden diese fehlen, würden Sie sich sicherlich die Frage stellen, welche Auswirkung die Multistore-Fähigkeit auf die Kundendaten bzw. Kundengruppen hat. Um es kurz zu machen: keine. Bei Kunden existiert die Multistore-Fähigkeit nicht, d. h., es können nicht pro Store View unterschiedliche Werte und Einstellungen hinterlegt werden. Kundendaten gelten global, d. h. übergreifend über alle Store Views und Websites.

Kunden lassen sich durch Websites trennen

Mithilfe von Websites lassen sich, das möchte ich an dieser Stelle erwähnen, da es thematisch ganz gut passt, Kunden bzw. Kundengruppen trennen. Wenn Sie mehrere Store Views haben, die an einer Website hängen, kann ein Kunde aus Store View A sich auch in Store View B anmelden. Das werden Sie auch nicht verhindern können. Bei Websites ist das jedoch anders, da Sie die Gültigkeit des Kundenkontos auf eine Website limitieren können. Der in Website A registrierte Kunde kann sich also ohne Neuregistrierung nicht in Website B anmelden.

17.2.4    Warenkorb-Preisregeln und Katalogpreisregeln

Bei den Preisregeln, das gilt für Warenkorb-Preisregeln wie für Katalogpreisregeln, setzt Magento auf einen etwas anderen Mechanismus. Bei den Produkten und Kategorien legen Sie immer einen Datensatz an und können diesen Datensatz anschließend übersetzen. Bei den Warenkorb-Preisregeln und Katalogpreisregeln müssen Sie aber jeweils einen Datensatz pro Website anlegen und diesem mitteilen, für welche Website er aktiviert werden soll. Wenn Sie recht viele Websites im System haben, führt das zwangsläufig zu einer großen Anzahl an Datensätzen, wobei sich die Anzahl der Websites in der Praxis doch immer recht in Grenzen hält.

Öffnen Sie im nächsten Schritt exemplarisch eine Warenkorb-Preisregel oder eine Katalogpreisregel, und scrollen Sie bis zum Abschnitt Websites. Sie sehen diesen ebenfalls in Abbildung 17.8, falls Sie mir an dieser Stelle nicht im eigenen System folgen. Wie Sie sehen, ist in der Regel eine Mehrfachauswahl enthalten, mit deren Hilfe Sie Magento mitteilen, für welche Website diese Regel aktiviert werden soll. Da in 90 % aller Fälle die Inhalte einer Regel nicht übersetzt werden müssen, einzige Ausnahme wäre, wenn Sie die Regelnamen im Frontend auslesen würden, reicht die Eingrenzung auf Website-Ebene. Wenn Sie aber eine Regel für eine Website überschreiben bzw. abändern möchten, so müssen Sie in diesem Fall einen zweiten Datensatz anlegen und diesem die jeweilige Website mittels Mehrfachauswahl mitteilen.

Im Falle meines spanischen Store Views werde ich bei den Preisregeln keine Änderungen vornehmen, da der Store View zur selben Website wie mein »Standard«-Store-View zählt und Differenzierungen somit gar nicht möglich wären.

Abbildung 17.8    Preisregeln lassen sich nicht übersetzen und nur auf Website-Ebene zuweisen.

17.2.5    Seiten

Neben den Produkten sind vor allem die Seiten die wichtigsten Inhalte, die pro Store View übersetzt werden müssen. Ähnlich wie bei den Preisregeln setzt Magento bei den Seiten auf einen etwas anderen Mechanismus als bei den Produkten und Kategorien. Rufen Sie im nächsten Schritt bitte die Startseite auf, indem Sie auf Inhalt • Elemente • Seiten klicken und dort den Eintrag der Startseite bearbeiten. Wie Sie den eigentlichen Inhalt editieren können, möchte ich an dieser Stelle nicht im Detail erklären, wichtiger ist aus meiner Sicht nun die Store-View-Zuordnung bzw. die Übersetzungsmöglichkeiten. Scrollen Sie hierfür zum Abschnitt Page in Websites, den Sie in Abbildung 17.9 sehen. Auch hier steht Ihnen, genau wie bei den Preisregeln, eine Mehrfachauswahl zur Verfügung. Das heißt, wenn Sie eine Seite anlegen, können Sie auswählen, für welche Store Views diese genutzt werden darf. Wenn Sie, nur als Beispiel, einen zusätzlichen Store View für Österreich und einen Store View für die Schweiz angelegt haben, so können Sie sicherlich die Startseite, die Sie in Deutsch realisiert haben, allen drei Store Views zuweisen. Auch wenn Sie eine englische Startseite pflegen und viele verschiedene englischsprachige Store Views besitzen, ergibt diese Mehrfachauswahl durchaus Sinn. In meinem Beispiel hingegen wäre es kontraproduktiv, wenn ich den Nutzern in Spanien, Frankreich und Deutschland dieselbe Startseite anzeigte, die in meinem Fall aktuell auf Deutsch gepflegt ist. Wählen Sie daher bei der Startseite nur den Store View Deutsch aus, und klicken Sie bitte anschließend auf Seite speichern.

Doch was passiert nun im spanischen Store View mit der Startseite? Um diese abzubilden, müssen Sie jetzt eine neue Seite anlegen. Die neue Seite muss über denselben URL-Schlüssel wie die »deutsche Startseite« verfügen, sprich home, die Inhalte können sich jedoch komplett unterscheiden. Bei der Shop-Ansicht wählen Sie den Eintrag Spanisch aus. Grundsätzlich sollten Sie immer dann, wenn Sie Seiten in weiteren Sprachen anlegen, denselben URL-Schlüssel wie die »Hauptseite« verwenden.

Abbildung 17.9    Eine Seite lässt sich per Mehrfachauswahl mehreren Store Views zuweisen.

URL-Schlüssel bei Seiten

An sich gibt es keine Limitierung, dieses Ihnen verbietet, pro Store View unterschiedliche URL-Schlüssel für ein und dieselbe Seite zu verwenden. Es erhöht jedoch enorm den Aufwand, wenn Sie dies tatsächlich tun. Am Beispiel der Startseite lässt sich das schön aufzeigen. Wenn Sie der Startseite nicht den CMS-Schlüssel home geben, müssen Sie erst in der Systemkonfiguration die Startseite neu definieren. Diesen Aufwand, bei Verlinkungen innerhalb von Seiten zieht das noch einen größeren Rattenschwanz mit sich, sollten Sie vermeiden. Nutzen Sie daher für eine Seite pro Store View den identischen URL-Schlüssel.

Sobald Sie die spanische Seite angelegt haben, wechseln Sie bitte in das Frontend. Wählen Sie dort über das Dropdown-Menü in der Kopfzeile den Eintrag »Spanisch« aus. Sofern Sie die Konfiguration korrekt hinterlegt haben, werden Sie daraufhin die spanische Startseite sehen, die ich gerade eben angelegt habe. Zugegebenermaßen ist diese recht unspektakulär, Sie sehen aber schon die übersetzte Überschrift bzw. den im Vergleich zur deutschen Seite abgeänderten Inhalt.

In der Praxis müssen Sie speziell bei den Seiten aufpassen und den Überblick bewahren. Wenn Sie 20 Sprachen, sprich 20 Store Views, im System haben, würde das bedeuten, dass Sie jede Seite 20-mal anlegen und auch 20-mal warten müssen. Daher ist der in Magento vorhandene Mechanismus und die dazugehörige Logik für nicht ganz so komplexe multilinguale CMS-Projekte durchaus gut und nutzbar, wenn jedoch die Menge an Seiten und Sprachen zunimmt, kann es, das ist zumindest meine Erfahrung aus der Praxis, etwas tricky werden.

Abbildung 17.10    Magento erlaubt die Anlage von einer Seite pro Store View, wodurch Übersetzungen ermöglicht werden.

17.2.6    Blöcke

Die Übersetzung von Blöcken folgt im Wesentlichen der Übersetzung von Seiten. Wenn Sie einen Block öffnen bzw. einen neuen Block anlegen, haben Sie eine Mehrfachauswahl, in der Sie die verschiedenen Store Views auswählen können. Dadurch definieren Sie, in welchem Store View ein Block angesprochen werden kann und somit zur Verfügung steht. Wenn Sie einen Block übersetzen möchten, müssen Sie pro Sprache bzw. Store View einen Block anlegen. Jeden dieser Blöcke weisen Sie anschließend dem gewünschten Store View zu. Denken Sie auch beim Block daran, die Kennung übergreifend zur Sprache beizubehalten. Das heißt, wenn Sie bei einem Block die Kennung »header-content« hinterlegt haben, sollten Sie bei jeder Sprachvariante dieses Blocks dieselbe Kennung verwenden. Ansonsten müssten Sie pro Store View den Block mit einem individuellen Code ansprechen, was zu Änderungen und Anpassungen in der Konfiguration, in den Seiten, aber auch in den Templates und im PHP-Code führen kann. Dieses Risiko sollten Sie nicht eingehen, verwenden Sie daher immer pro Sprache die identische Kennung.

17.2.7    Widgets

Das Handling von Widgets ist im Prinzip deckungsgleich mit dem von Blöcken. Die einzige Ausnahme besteht in der fehlenden Kennung bzw. dem fehlenden URL-Key, das müssen Sie bei Widgets nicht berücksichtigen. Ansonsten müssen Sie pro Store View ein Widget anlegen, d. h., es muss pro Sprache ein Datensatz bestehen, wenn Sie eine Übersetzung bzw. Anpassung vornehmen möchten. Die Definition, welches Widget in welchem Store View erscheint, erfolgt wiederum mit einer Mehrfachauswahl bei der Anlage bzw. Bearbeitung eines Widgets, wie Sie auch in Abbildung 17.11 sehen.

Abbildung 17.11    Pro Store View müssen Sie ein Widget anlegen, außer Sie weisen das Widget allen Store Views zu.

Wenn Sie ein Widget in allen Store Views nutzen möchten, müssen Sie dieses natürlich nicht mehrmals anlegen. Sie würden einfach mit der Mehrfachauswahl alle relevanten Store Views auswählen, sodass das Widget jedem Store View zur Verfügung steht. Nur wenn Sie das Widget übersetzen möchten, müssen Sie einen neuen Datensatz erstellen, wodurch pro Sprache ein Widget gepflegt werden muss.

17.2.8    Konfiguration

Inhalte wie Produkte, Seiten und Blöcke sind ein Thema, ein anderes Thema ist die Konfiguration. Und an und für sich ist die Konfiguration der, zumindest meiner Meinung nach, interessanteste Part der Multistore-Fähigkeit von Magento. Ich hatte bislang immer davon gesprochen, dass Sie Store Views für Sprachen verwenden können. Das ist auch der Grundgedanke, den Magento hatte. Sie können aber Store Views natürlich auch dazu nutzen, einen B2B- oder B2C-Bereich abzubilden. Oder Sie bauen gar keinen Markenshop bzw. Shop in Shop auf. Store Views sind ja letztendlich nur Konfigurationsebenen, die genutzt werden können, damit im Frontend später eine Auswahl bereitsteht, um zwischen den Konfigurationsebenen zu wechseln. Speziell aus diesem Grund finde ich den Aspekt der Konfiguration so wichtig, da Sie eben auch Store Views erstellen können, die über dieselben Produkte bzw. Produktinformationen oder auch Seiten verfügen, sich jedoch in der Konfiguration unterscheiden.

Rufen Sie jetzt bitte die Systemkonfiguration auf, indem Sie auf Shops • Einstellungen • Konfiguration klicken. Anschließend gelangen Sie zur Systemkonfiguration, die Sie ja bereits ausgiebig kennengelernt haben. In der Systemkonfiguration, gegebenenfalls ist Ihnen das bereits im Verlauf der letzten Kapitel aufgefallen, haben Sie in der linken oberen Ecke nun ebenfalls ein Auswahlmenü, in dem Sie eine Website bzw. einen Store View auswählen können. Das Verhalten ist, verglichen mit der Produktverwaltung, jedoch ein wenig anders. Auf der obersten Ebene existiert in dem Auswahlmenü der Eintrag Standardkonfiguration. Alle bislang gespeicherten Optionen haben Sie immer auf dieser Konfigurationsebene gespeichert. Die Standardkonfiguration ist also die höchste Ebene, auf der Sie Einstellungen bzw. Optionen speichern können. Unter dieser Ebene folgen die Websites, die ebenfalls Einstellungen speichern können. Der darunter folgende Store ist ausgegraut, dieser kann keine Einstellungen speichern, die dem Store zugewiesenen Store Views hingegen schon. Somit ergeben sich insgesamt drei Ebenen, auf denen Sie Konfigurationseinstellungen speichern können. Die oberste Ebene vererbt, so wie dies in Magento üblich ist, Optionen weiter. Angenommen, Sie möchten den spanischen Store View anpassen, dann müssen Sie also nicht alle Optionen erneut setzen, sondern nur diejenigen Optionen abändern, die Sie editieren möchten. Durch diese Vererbungslogik sparen Sie sich in der Praxis eine Menge Zeit, da Sie allgemeingültige Einstellungen auf der obersten Ebene setzen und anschließend auf der Store-View- bzw. Website-Ebene einfach nur noch die notwendigen Anpassungen vornehmen müssen.

So weit die Theorie, was das in der Praxis bedeutet, möchte ich Ihnen am einfachen Beispiel der Sprache im Frontend zeigen. Klicken Sie nun innerhalb der Systemkonfiguration auf Allgemein • Allgemein, und scrollen Sie zum Abschnitt Regionale Optionen. Dort angekommen, sehen Sie das Dropdown-Menü bei Region. Die Region, an dieser Stelle ist das Feld etwas unsauber übersetzt, definiert schlussendlich das Sprachpaket, das geladen werden soll. Da Sie jetzt für den spanischen Store View eine andere Sprache einstellen möchten, müssen Sie mithilfe des Dropdown-Menüs, das sich in der linken oberen Ecke befindet, zuerst den spanischen Store View auswählen. Wechseln Sie daher im nächsten Schritt bitte den Store View, wobei Sie natürlich auch einen beliebig anderen Store View wählen können. Magento lädt nun die Seite neu, und Sie sehen weiterhin den Abschnitt Regionale Optionen. Entfernen Sie beim Feld Region den Haken bei der Checkbox Website verwenden. Dadurch teilen Sie Magento mit, dass Sie den gesetzten Standard-Wert für diesen Store View explizit überschreiben möchten. Wenn Sie den Haken nicht entfernen, können Sie das Dropdown-Menü gar nicht erst verwenden, d. h., sobald Sie einen Wert auf Store-View- oder Website-Ebene überschreiben möchten, müssen Sie immer den Haken bei der jeweiligen Checkbox entfernen. Wählen Sie nun im Dropdown-Menü den Eintrag Englisch (Vereinigte Staaten) aus, und speichern Sie die Konfiguration.

Halt, stop! Warum Englisch und nicht Spanisch?!

Magento verfügt von Haus aus über keinerlei Sprachpakete bzw. Übersetzungen. Würden Sie an dieser Stelle nun die spanische Sprache auswählen, kennt Magento zwar Ihren Wunsch, Übersetzungen sind aber nicht vorhanden. Dementsprechend müssen Sie zuerst das spanische Sprachpaket installieren, damit das Frontend auch in spanischer Sprache erscheint. Da ich Ihnen an dieser Stelle nicht mit der Installation der Sprachpakete das Kapitel erschweren möchte, nutzen Sie an dieser Stelle einfach die englische Sprache, denn diese ist im Standard enthalten. Dadurch sehen Sie also die Auswirkungen, und wie Sie das spanische Sprachpaket bzw. Sprachpakete an sich installieren, werden Sie im weiteren Verlauf des Buches noch kennenlernen.

Nachdem Sie die Konfiguration gespeichert haben, wird eine Meldung erscheinen, dass Sie den Cache leeren müssen. Folgen Sie bitte diesem Hinweis, da Sie ansonsten im Frontend keine Veränderung sehen werden. Sobald Sie den Cache geleert haben, rufen Sie das Frontend auf und wählen innerhalb des Frontends den spanischen Store View aus. Wenn Sie nun z. B. in die Kundenregistrierung gehen, werden Sie lauter englische Bezeichnungen und Übersetzungen vorfinden, wie Sie auch in Abbildung 17.12 sehen können. Wechseln Sie hingegen auf den deutschen Store View zurück, so wird das Frontend in deutscher Sprache dargestellt. Sie sehen also, dass einzig und allein aufgrund eines Konfigurationsparameters das Verhalten des Frontends entsprechend angepasst und individualisiert werden kann. Innerhalb von Magento können Sie natürlich nicht nur die Sprache pro Store View definieren, sondern knapp 100 % aller Einstellungen und Optionen, die in der Systemkonfiguration vorhanden sind.

Es gibt nur vereinzelte Ausnahmen, ähnlich wie bei Produktattributen, in denen globale Werte gelten, die Sie nicht überschreiben können. Auch gibt es Differenzierungen, welche Angaben Sie auf der Website-Ebene und welche Sie auf der Store-View-Ebene editieren können. Beispielsweise, einfach damit Sie an dieser Stelle eine Vorstellung haben, lassen sich in der Regel Zugangsdaten zu Payment-Service-Providern (PSP), also Zahlungsdienstleistern, höchstens auf Website-Ebene, nicht aber auf Store-View-Ebene hinterlegen. An dieser Stelle würde es schlicht keinen Sinn ergeben, wenn man pro Sprache, also pro Store View, Verbindungsdaten zum PSP hinterlegen würde. Neben diesem Beispiel gibt es noch ein paar wenige weitere Beispiele, grundsätzlich können Sie jedoch auf Store-View-Ebene so gut wie alle Optionen und Konfigurationseinstellungen, die Sie auf der höchsten Ebene gesetzt haben, überschreiben.

Abbildung 17.12    Sprachen und weitere Optionen können pro Store View gesetzt werden.

17.2.9    Themes

Auch Themes spielen bei der Multistore-Fähigkeit von Magento eine gewisse Rolle, da Sie die Theme-Optionen bzw. das Theme an sich pro Store View definieren können. Rufen Sie hierzu den Link Inhalt • Design • Konfiguration auf. Daraufhin erhalten Sie eine Auflistung aller Store Views und der zugewiesenen Themes, wie Sie auch in Abbildung 17.13 sehen. Die Funktionsweise unterscheidet sich an dieser Stelle also erneut von den bereits bekannten Funktionsweisen, zumindest in gewissen Teilen.

So überschreiben Sie nicht Optionen, indem Sie in einem Theme mittels Dropdown-Menü den Store View wechseln. Sie müssen, das geht in die Richtung wie bei den Seiten, den entsprechenden Eintrag auswählen, wobei jeder Store View einen eigenen Eintrag erhält, und können dadurch Store-View-spezifische Änderungen vornehmen. Auch hier wird rein auf der Store-View- und nicht auf der Website-Ebene gearbeitet. Im Gegensatz zu den Seiten müssen Sie jedoch die Einträge nicht selbst anlegen. Sobald Sie einen Store View erstellen, legt Magento bei den Themes automatisch einen neuen Eintrag an, auf den Sie an dieser Stelle zugreifen können.

Abbildung 17.13    Pro Store View wird ein Eintrag bei den Themes angelegt.

17.2.10    Sonstige Bereiche und allgemeine Logik von Magento

Zugegebenermaßen möchte ich Sie an dieser Stelle nicht nochmals mit jeder Ansicht im Magento-Backend konfrontieren und auf die Möglichkeiten der Store-View-spezifischen Werte hinweisen. Grundsätzlich können Sie in Magento so gut wie jedes Element einer Website bzw. einem Store View zuweisen und dieses Element auf diesen Ebenen überschreiben. Das gilt für Produkte und Kategorien, aber auch für Transaktions-E‐Mails, Bestellbedingungen etc. Die Multistore-Fähigkeit ist einer der großen USPs von Magento, dementsprechend umfangreich und mächtig ist diese Funktion auch ausgebaut. Dadurch, vertrauen Sie mir an dieser Stelle, können Sie alle notwendigen und möglichen Optionen bis auf die kleinste Ebene, sprich die Store Views, anpassen. Entweder erfolgt die Anpassung über ein Dropdown-Menü, das sich in der linken oberen Ecke befindet und den Wechsel der Store Views ermöglicht, oder mittels eigener Datensätze pro Store View. Letzteres ist beispielsweise bei den Seiten, Blöcken, aber auch bei den Bestellbedingungen der Fall. Zugegebenermaßen hätte Magento, das ist zumindest meine Meinung, das Thema etwas konsistenter lösen können. Letztendlich sollte es Sie aber nicht davon abhalten, die vollen Funktionen der Multistore-Fähigkeit nutzen zu können. Je nach Ansicht sehen Sie eigentlich direkt, ob Sie mit zusätzlichen Datensätzen arbeiten müssen oder ob Sie bestehende Optionen und Einstellungen überschreiben können.
